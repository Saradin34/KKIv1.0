# Онлайн: рейтинг, друзья, матчмейкинг — спецификация v3.3

## 1. Архитектура

```
Клиент (prototype / Unity)
  │  HTTPS + JWT (Authorization: Bearer <access>)
  ▼
meta-server :8081  (server/meta_server.ts + server/social.ts + server/auth_jwt.ts)
  · аккаунты, JWT (access 15 мин / refresh 30 дн, ротация)
  · друзья, заявки, присутствие, вызовы
  · очередь матчмейкинга, рейтинг Elo, лидеры
  · выдаёт БИЛЕТ на матч (JWT typ=match, 5 мин)
  ▲                                   │ билет
  │ POST /api/internal/match-result   ▼
  │ (x-internal-key)            Клиент ──WebSocket──► match-server :8080
  └──────────────────────────────────────────────── (server/match_server.ts)
                                        · единственный источник истины боя (GameEngine)
                                        · пускает только по билету, место = из билета
                                        · сообщает итог в meta-server
```

Обязательные переменные в продакшене: `JWT_SECRET` (одинаковый у meta и match, ≥32 символа),
`INTERNAL_KEY` (опционально, иначе выводится из секрета), `META_URL` для match-server.

## 2. Аккаунты и авторизация
- `POST /api/auth/register | login` → `{accessToken, refreshToken, expiresIn}`.
- `POST /api/auth/refresh {refreshToken}` — одноразовый refresh; повторное использование
  погашенного токена отзывает все сессии пользователя (защита от кражи).
- `POST /api/auth/logout {refreshToken, all?}`, `GET /api/auth/me`.
- Онлайн-ручки доступны только авторизованным. Гости играют офлайн против ИИ.

## 3. Друзья и присутствие
| Ручка | Что делает |
|---|---|
| `GET /api/users/search?q=` | поиск по логину/нику (≥2 символа, до 20 результатов) |
| `POST /api/friends/request {to}` | заявка; встречная заявка → сразу дружба |
| `POST /api/friends/accept\|decline {from}` | ответ на заявку |
| `POST /api/friends/cancel {to}` | отозвать свою заявку |
| `POST /api/friends/remove {login}` | удалить (у обоих) |
| `GET /api/friends` | друзья со статусом и рангом, входящие/исходящие заявки, вызовы |
| `POST /api/presence {status}` | пульс раз в 30 с; «не в сети» через 70 с без запросов |

Статусы: `online`, `searching`, `in_match`, `offline`. Лимиты: 200 друзей, 50 исходящих заявок.

## 4. Рейтинг
- Старт 1200 MMR. Elo: K=40 первые 20 игр (калибровка), далее K=24.
- Серия 3+ побед: +4 (до Алмаза). Минимум ±1 за матч.
- Ранги: Бронза (<1100) · Серебро (1100) · Золото (1300) · Платина (1500) · Алмаз (1700) · Мифик (1900+, показывается MMR).
  Внутри ранга 4 дивизиона (4 → 1).
- Сезон (`SEASON`): мягкий сброс — половина пути к 1200.
- Рейтинг меняет ТОЛЬКО match-server (`/api/internal/match-result`), клиент не может прислать победу.
- `GET /api/rating/me` — MMR, ранг, место, история 20 матчей. `GET /api/leaderboard` — топ-100 сезона.

## 5. Матчмейкинг и вызовы
- `POST /api/mm/queue {mode: ranked|casual, deckId}` → `GET /api/mm/status` (опрос 2,5 с) → `found`
  с `{match, seat, ticket, opponent}` (билет отдаётся один раз). `POST /api/mm/cancel`.
- Подбор каждую секунду: рейтинг — окно ±50 MMR, растёт на 10/с до ±400; обычный — ±1000.
- Дружеский вызов: `POST /api/challenge {to}` (только другу в сети) → у друга баннер →
  `POST /api/challenge/accept {id}` → оба получают `found` (mode=friendly, без рейтинга). Вызов живёт 2 мин.

## 6. Бой по сети (следующий этап)
Сделано на сервере: вход по билету, проверка колоды, авторитетный `GameEngine`, 60 с на переподключение,
иначе техническое поражение, отчёт итога в meta-server.

Что осталось подключить в клиенте (`BattleUI` в prototype.ts):
1. `NetBattle`: WebSocket к match-server, `{t:'join', ticket, deck}`.
2. Вместо `aiTurn()` — `netTurn()`: применять к экрану события соперника, пришедшие от сервера.
3. Свои действия (розыгрыш, цели, атаки, муллиган, ответы в окне мгновенных) отправлять как
   `{t:'act', action}` и отображать только после подтверждения сервера.
4. Скрытая информация: сервер шлёт каждому игроку свой снапшот (рука соперника — только число карт).
5. Таймер хода («верёвка») на сервере: 75 с + 15 с запаса, по истечении ход завершается автоматически.

## 7. Хранилище
Сейчас — `server/data/social.json` (+ accounts.json). При `DATABASE_URL` — перенести в PostgreSQL:
`friends(a,b)`, `friend_requests(from,to,ts)`, `ratings(login,season,mmr,…)`, `matches(id,mode,a,b,winner,dA,dB,ts)`.
Очередь и присутствие при нескольких нодах — в Redis.

## 8. Защита
- Rate-limit на POST (10/мин для auth, 60/мин прочие).
- Билет матча: 5 мин, привязан к логину, матчу и месту; занятое место чужим билетом не перехватить.
- Итог матча — только server→server с ключом.

Интеграционный тест: `node tools/online_test.js` (запущены оба сервера, чистый `server/data`).

## 6.1 PvP-бой (v3.4, реализовано)
- Схема: «авторитетный активный игрок». Кто ходит, тот применяет действие локально и шлёт `{t:'net', m:{k, ...действие, st: exportState()}}`. Второй клиент проигрывает действие зеркально (для анимаций) и выравнивается по `importState(st, mirror=true)`, поэтому рассинхрон невозможен.
- Seat0 раздаёт стартовое состояние (`init`). Муллиган у каждого свой (`mull`). Первым ходит seat0.
- В сетевом бою окна мгновенных ответов на стеке отключены.
- match_server ретранслирует ходы и ждёт переподключения 60 с (`RECONNECT_GRACE_MS`). Если соперник не вернулся, ему засчитывается техпоражение. Есть `concede`. Итог — по согласию обоих клиентов: если прислал только один, он принимается через 15 с. Затем POST в meta `/api/internal/match-result`, а meta пересчитывает Elo.
- Ограничения: снимок содержит руку и колоду соперника, их можно подсмотреть через devtools. Сервер не проверяет ходы (`stateHash` зарезервирован). Для честного рейтинга нужна серверная симуляция движка.
- v3.5.1: PvP-ретранслятор (`server/match_relay.ts`) встроен в meta-server — `ws://host:8081/match`. Отдельный `npm run server:match` (порт 8080) остаётся для выноса на другой хост.

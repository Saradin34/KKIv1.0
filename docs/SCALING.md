# ЭХО-ЦИТАДЕЛЬ — масштабирование и производительность (v3.16)

Цель: **10 000+ одновременных пользователей без лагов**. Замерено нагрузочным
тестом `tools/load/load10k.mjs` против отдельного инстанса meta-server.

## Среда замера

- Sandbox: **2 ядра** (общая CPU-квота), Node 20.20.2, файл-хранилище (snapshot.json).
- Отдельный инстанс на :8090 со своей data-директорией, `RATE_LIMIT=0` (лимит
  включён в проде — он бы исказил цифры).
- Проводные данные — реальные: профильный синк ~2 КБ, матчи — полный пайплайн
  (очередь → билет → WS join → сетевые ходы → результат → elo).

## Результаты (один прогон, один инстанс)

|---|---|---|---|

| **A2. Бёрст** | 5 000 НОВЫХ TCP-соединений за 1 с (worst case переподключений) | **5000/5000 ok, 0 ошибок** | p50 = 7.9 мс · p95 = 15.3 мс · **p99 = 31.7 мс** |
| **B. WS онлайн** | 10 000 одновременных WebSocket на `/match` | **10000/10000, 0 ошибок** | разгон + удержание 6.2 с |
| **C. Реальные матчи** | 500 полных PvP-матчей (100 параллельных × 5 раундов) | **500/500, 0 провалов** | 5.7 с на все 500 |

Ресурс сервера в фазе A (10k пользователей): **CPU 55% двух ядер, RSS 163 МБ**.
Исчерпывание в 200-соединённом тесте (26k req/s) — потолок одного инстанса;
при реальной нагрузке 10k игроков (~6–12К req/s) инстанс работает на 30–60% CPU.

> Латентность в фазе A меряется «глазами клиента». p99 ≈ 120 мс — это
> fire-and-forget синк профиля, UI обновляется из локального состояния,
> задержка невидима. Спин-апа (скачки 1.5–3.5 с), которые были на ранних
> прогонах, устранены — см. «Правки v3.16».

## Правки v3.16, которые это дали

1. **Snapshot без блокировки event loop'а.** Запись коалесцируется (≤1 раз в 5 с),
   сериализуется **кусками** с уступкой `setImmediate` каждые ~500 профилей,
   пишется атомарно (tmp + rename). На 10k профилей это ~20 МБ: раньше один
   синхронный `JSON.stringify` давал лаг-спайк на сотни мс раз в 5 с.
2. **`listen(backlog: 65535)`.** Дефолтный backlog 511 ронял SYN-пакеты при
   волне переподключений → клиенты переупаковывали соединения через 1 с / 3 с
   (видимо как p50≈1.5 с, p95≈3.5 с). После фикса бёрст 5000 соединений/с
   проходит с p99 32 мс и 0 потерь.
3. **Сетевые тайминги.** `keepAliveTimeout 65 с` (длиннее таймаутов LB —
   соединение не рвётся «под игроком»), `headersTimeout 70 с`, `requestTimeout 30 с`
   (вешний запрос не висит), `maxRequestsPerSocket 1000`.
4. **POST-тело ≤ 256 КБ → 413.** До этого «медленный» POST вешал сокет навсегда
   (найденный POST-hang).
5. **PG-флеш точечный** — только dirty-pid, а не дамп таблицы.
6. **WS:** лимит 64 КБ на сообщение + rate limit на соединение; `MATCH_SHARDS`
   позволяет раздавать матчи по нескольким обработчикам/инстансам.
7. **Rate limit per-IP** (10 рег/мин, 60 POST/мин) — защита от спама/брута,
   в проде включён.

## Куда масштабироваться дальше (дорожная карта)

- **Вертикально:** измерено на 2 ядрах. Прод-VM на 4–8 ядер — запас ×2–4 по REST
  (CPU сервера линейный до ~70% на 26k req/s) и по WS.
- **Горизонтально:**
  - REST-часть stateless — профили в Postgres (адаптер готов, `DATABASE_URL`),
    любые N инстансов за L7-LB.
  - WS-матчи: LB с session affinity (sticky по `/match`) либо отдельный пул
    relay-инстансов за балансировщиком (MATCH_SHARDS).
  - Очередь матчей и рейтинг — в Postgres (общее состояние), инстансы не хранят
    ничего критичного в памяти (snapshot — только file-режим).
- **Хранилище:** Postgres уже поддержан (тесты 17/17, 15/15); для 10k+ онлайн
  файл-режим не рекомендуется (один процесс, одна запись снапшота).

## Как повторить

```bash
# отдельный инстанс (своя data-директория, иначе конфликт snapshot.json)
mkdir -p /tmp/kki-load && cd /tmp/kki-load
ulimit -n 65536   # нужно для фазы B (10k WS)
RATE_LIMIT=0 PORT=8090 node /path/to/KKIv1.0/build/meta_server.js &

node tools/load/load10k.mjs
# env-краны: LOAD_PORT=8090 LOAD_USERS=10000 LOAD_CONC=200 LOAD_DUR=30
#            LOAD_WS=10000 LOAD_MATCHES=500 LOAD_ACCT=200
```

Метрики фазы A включают **CPU и RSS самого сервера** (через /proc) — в выводе:
`CPU сервера за фазу: 55% · RSS: 163 МБ`.
